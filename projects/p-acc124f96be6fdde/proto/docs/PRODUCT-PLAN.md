# 学生社团 2.0 桌面端设计计划

更新时间：2026-09-23

## 1. 已确认的推进方式

- 先完成教师桌面端和学生桌面端，手机端滞后。
- 桌面端用于先确认业务对象、主流程、权限和数据承接；手机端后续根据具体任务重新组织交互，不直接缩小桌面页面。
- 教师端补充运行分析报告专项入口；学生端补充个人社团报告。报告复用社团、成员、活动、签到、成果和学分数据，不要求学生重复填写总结。
- 家长手机端的业务范围已明确为后台授权后的有限代办与孩子报告查看：可代申报、代报名，但不复制学生的审核和社团运营能力。
- 每个业务部分开始前，用户提供 1.0 实现和自己的想法。
- 先进行产品评估和综合讨论，确认方向后再设计该部分的 2.0 原型。
- 当前允许先实现再随调研修改，但不提前实现高成本、强耦合且证据不足的能力。

## 2. 主流程设计顺序

1. 教师配置。
2. 学生申报社团，审核通过后成为团长。
3. 普通学生申请加入社团，团长审核通过后成为团员。
4. 教师审核社团申报。
5. 教师审核社团学分。

以上是设计与验证顺序，不代表所有页面、字段和规则已经确认。

## 3. 每部分的设计门槛

开始一部分原型前，至少完成：

1. 识别 1.0 页面解决的用户任务和业务对象。
2. 区分 1.0 中必须保留、需要重组、重复和待验证的能力。
3. 汇总用户的新想法及其解决的问题。
4. 判断对其他角色、页面、状态、权限和历史数据的影响。
5. 输出一项主推荐方案、风险和待确认项。
6. 用户确认方向后，再进入原型实现与验证。

## 4. 校 2：按学院负责社团的需求分析

### 调研事实

- 学校分为文史、艺术等五个学院。
- 过去由一名教师先统一接收学生自由申报的社团。
- 该教师将申报数据导出，再按学院分类交给相应教师。
- 各学院负责人不仅参与审核，还会在开学季、万圣节等时间带动社长进行活动规划和组织。

### 当前产品判断

- 该需求的核心是“按社团类别自动确定负责教师和管理范围”，不是让学生自由选择一位教师。
- 第一选择是在“社团类别”上增加可选的“类别负责人／负责教师”。学生选择社团类别后，系统自动带出负责关系，不再要求学生选择具体教师。
- 负责教师为空时，系统应继续支持原有统一审核方式，避免把某所学校的组织结构变成所有学校的必选规则。
- 该负责关系可能同时影响申报审核的数据范围和社团后续组织管理，因此不能只作为普通展示字段。

### 需要继续确认

- 一个类别能否配置多名负责教师。
- 多名教师是共同可处理，还是需要主负责人和协同教师。
- 负责人是否自动获得该类别所有社团的查看、审核和后续管理权限。
- 类别负责人变更后，历史审核记录和已成立社团如何保留原负责人信息。
- 学校 1 提到的“学生自行邀请指导教师”是否是另一种独立关系；当前不将两者合并。

## 5. 公共表单能力的复用判断

### 参考能力

截图中的公共表单采用两步结构：先设置业务表单基础信息，再通过标题、文本、富文本、单选、多选、日期、附件等组件配置扩展内容。

### 推荐方式

复用公共表单引擎，但采用“固定业务字段 + 扩展字段”的组合：

- 固定业务字段由学生社团产品维护，用于后续筛选、审核、权限、统计和流程判断。
- 学校差异化材料使用公共表单扩展字段，例如海报、协议、补充说明和附件。
- 教师配置扩展字段时，应能设置显示、必填、顺序和说明。
- 学生提交后保存当时的表单结构快照；后续配置变更不能改写历史申请。
- 教师审核页需要按提交时的结构只读呈现扩展字段。

不建议将社团名称、社团类别、申报人、团长、人数上限等核心业务字段全部交给自由表单维护。

### 复用前需要核实的公共能力

- 是否支持绑定具体业务对象和业务流程。
- 是否支持必填、显示条件、附件类型与数量限制。
- 是否支持已发布表单的版本或历史快照。
- 是否能在学生填写端与教师审核端使用同一份字段定义。
- 是否支持固定字段与自定义字段组合排序。
